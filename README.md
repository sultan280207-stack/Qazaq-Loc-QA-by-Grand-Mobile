# locqa

Утилита для проверки переводов Flutter-приложений в формате ARB. Сравнивает перевод с исходным
файлом и ищет 11 типов ошибок из кейса Qazaq Loc QA. Работает с любым ARB без правок кода.
Для казахского включаются дополнительные проверки: русские буквы вместо казахских, сингармонизм,
окончания после плейсхолдеров и перевод в латиницу 2021 года.

Это решение кейса 02 «Qazaq Loc QA» от Grand Mobile на Decentrathon 6.0. Как мы искали
и исправляли ошибки, написано в [METHODOLOGY.md](METHODOLOGY.md). Данных кейса (ARB-файлов, отчёта,
исправленного файла, глоссария) здесь нет: по условиям кейса их нельзя публиковать, поэтому они
отправлены организаторам отдельно. Все строки в `tests/fixtures` выдуманы.

Нужен только Python 3.10 или новее, сторонних библиотек нет. LLM утилита не вызывает, так что
прогон ничего не стоит.

## Установка

```bash
pip install git+https://github.com/sultan280207-stack/Qazaq-Loc-QA-by-Grand-Mobile.git
# или из скачанной папки: pip install .   (pip install -e .[test], если нужны тесты)
locqa --version
```

## Как запускать

```bash
locqa check --source intl_ru.arb --target intl_kk.arb --glossary glossary.csv \
            --ref intl_uz.arb --ref intl_en.arb --out report.json        # заодно пишет report.html

locqa fix --source intl_ru.arb --target intl_kk.arb --report report.json \
          --out intl_kk_fixed.arb                                        # применяет suggestion из отчёта

locqa validate --template intl_ru.arb intl_kk_fixed.arb                  # проверка примерно как в gen-l10n
locqa translit --target intl_kk_fixed.arb --out latin_long.json --out-arb intl_kk_Latn.arb
locqa review-page --report report.json --out review.html --name intl_kk.arb  # страница для носителя
```

`--ref` подключает другие переводы того же файла. По ним утилита узнаёт текст на чужом языке
(например, узбекскую строку в казахском файле) и сравнивает длину.

У `check` есть ещё опции:

- `--only` оставляет только перечисленные типы;
- `--min-severity` отсекает мелочи;
- `--fail-on high` возвращает код 1, если есть серьёзные ошибки (удобно для CI);
- `--review review.csv` подключает решения ревьюера. Можно указать несколько файлов, тогда при
  расхождении побеждает тот, что указан позже;
- `--review-sheet sheet.csv` выгружает лист для проверки носителем.

## Что проверяется

| Тип | Как ищем |
|---|---|
| `untranslated` | ключ есть в исходнике, а в переводе его нет. Ещё пустой перевод, если в исходнике три слова или больше |
| `same_as_source` | перевод совпадает с исходником. Бренды, числа и слова, которые так же пишут в других строках перевода (Финал, Гараж), не трогаем. Ловим русские окончания, служебные слова и фразы из трёх и больше непривычных слов |
| `placeholder_mismatch` | сверяем `{name}`, `%s` и теги `<g>`. Замечаем потерянные скобки (`time` вместо `{time}`) и опечатки в имени (`{leve}`), исправление предлагаем сами |
| `plural_mismatch` | свой ICU-парсер: в переводе нет `plural`, нет формы `other`, лишние категории или не хватает форм по CLDR для языка перевода |
| `glossary_violation` | по `glossary.csv`: термин из исходника не перевели как надо (`strict=yes`) или нашли запрещённый вариант (`kk_avoid`) |
| `length_overflow` | короткая кнопка или заголовок (до 30 символов и 4 слов) стали длиннее исходника в 3 раза и больше, и длиннее, чем во всех других языках. Если один и тот же хвост прилеплен к нескольким строкам, предлагаем его отрезать |
| `machine_translation_suspect` | поменялись числа; в казахском тексте остались русские слова; перевод подтянут от ключа с другим смыслом (сверяем ru, en и uz); кальки из глоссария |
| `inconsistent_term` | одна и та же короткая строка переведена по-разному. Синонимы, которые разрешает глоссарий, не считаются. Отдельно ловим повторяющиеся ключи с разными значениями |
| `suffix_harmony` | готовое окончание сразу после плейсхолдера (`{name}-ға`, `{price}-ге`, `%s-тан`). Предлагаем переписать через послелог (`{price} үшін`, `{time} дейін`, «Ең көбі {max} …») |
| `orthography` | латинские буквы-двойники в кириллическом слове; русская буква вместо казахской (сагат → сағат, если правильный вариант есть в файле хотя бы три раза); строчная буква в слове капсом; сингармонизм внутри слова (мектепта → мектепте) |
| `wrong_language` | латиница в кириллическом файле и наоборот. Язык угадываем по характерным словам (uz, pt/es, en) и по совпадению со строкой из `--ref` |

Severity: `high` ломает строку или смысл, `medium` заметная ошибка, `low` стиль и единообразие.
`confidence` показывает, насколько детектор уверен, от 0 до 1.

## report.json

Это массив находок. Обязательные поля такие же, как в ТЗ, плюс три своих, которые помогают в работе.
Пример из тестовых файлов:

```json
{
  "key": "shopTab", "issue_type": "length_overflow", "severity": "high",
  "source": "В магазин", "target": "Дүкенге өту бөлімін ашу үшін түртіңіз",
  "evidence": "В исходнике 9 символов, в переводе 37 (в 4.1 раза длиннее), в других языках максимум 9. Это кнопка или заголовок, места там мало. Хвост «бөлімін ашу үшін түртіңіз» прилеплен ещё к нескольким таким строкам, похоже на мусор.",
  "suggestion": "Дүкенге өту", "confidence": 0.9, "reviewed_by_human": false,
  "line": 15, "detector": "length", "origin": "auto"
}
```

`origin` бывает трёх видов: `auto` нашёл только детектор, `auto+review` ревьюер подтвердил,
`review` ревьюер добавил сам.

## Проверка человеком

Проще всего через страницу:

1. `locqa review-page --report report.json --out review.html` делает один HTML-файл. Он открывается
   в браузере без интернета и никуда ничего не отправляет.
2. Носитель идёт по строкам и жмёт «Верно» или «Не нужно», при необходимости правит текст. Если
   в тексте пропал плейсхолдер, страница сразу предупредит. Отметки хранятся в браузере, можно
   прерваться и продолжить.
3. Кнопка «Скачать результат» отдаёт `native_review.csv` в формате для `--review`.
4. `locqa check … --review review.csv --review native_review.csv --out report.json`: отклонённые
   находки пропадают, подтверждённые получают флаг `reviewed_by_human`, добавленные попадают
   в отчёт с `origin=review`.
5. `locqa fix … --report report.json --out intl_kk_fixed.arb`. С `--only-reviewed` применятся только
   правки, которые проверил человек.

Если удобнее в таблице, `locqa check … --review-sheet sheet.csv` выгружает все находки в CSV.
В нём носитель ставит `verdict` (`confirm`, `reject` или `add`), правит `suggestion`, ставит
`reviewed_by_human=true` и пишет имя в `reviewer`.

Каждая изменённая или добавленная строка в исправленном файле получает метаданные. Это атрибуты
с `x-`, спецификация ARB их разрешает, а `flutter gen-l10n` их пропускает:

```json
"greeting": "Сәлем, {name}!",
"@greeting": {"x-reviewed_by_human": false, "x-locqa-issues": "placeholder_mismatch", "x-locqa-original": "Сәлем, name!"},
```

Порядок строк и форматирование файла не меняются. Если ключ повторяется, новый текст ставим во все
вхождения, чтобы в файле не оставалось двух разных переводов, а метаданные пишем один раз после
последнего (Flutter читает именно его).

## Глоссарий

В `glossary.csv` обязательны колонки `ru, kk, en, comment`. Можно добавить `ru_match`, `kk_match`,
`kk_avoid` (регулярки), `strict` (yes/no), `issue_type` и `severity`. Вместо `kk` может стоять код
любого языка: `uz`, `uz_match` и так далее. Пример лежит в `tests/fixtures/glossary.csv`.

## CI

В этом репозитории `.github/workflows/tests.yml` на каждый push гоняет тесты на Python 3.10 и 3.12
и делает пробный прогон по тестовым файлам. Отчёт и страница для ревью из этого прогона лежат
в артефактах сборки.

Для репозитория с Flutter-приложением есть готовый пример `examples/flutter-app-workflow.yml`.
Его нужно скопировать в `.github/workflows/` приложения. На каждый pull request, где поменялись
`*.arb`, он:

- запускает `locqa check --fail-on high` и `locqa validate`;
- прикладывает JSON- и HTML-отчёты к сборке;
- отдельной задачей запускает настоящий `flutter gen-l10n`.

Если Flutter стоит локально, то же самое можно проверить без CI:

```bash
bash scripts/gen_l10n_check.sh intl_ru.arb intl_kk_fixed.arb
```

Скрипт создаёт временный Flutter-проект, кладёт туда файлы, запускает `flutter gen-l10n`
и `flutter analyze`, а потом удаляет проект.

## Тесты

```bash
pip install -e .[test] && python -m pytest -q     # 29 тестов на выдуманных данных
```

Данные заказчика в репозиторий не кладём, это условие кейса. Всё в `tests/fixtures` выдумано.

## Ограничения

- `machine_translation_suspect` на эвристиках ловит только часть калек. Остальное закрывают глоссарий
  (`kk_avoid`) и ручная проверка.
- `validate` повторяет основные правила gen-l10n (синтаксис ICU, плейсхолдеры против шаблона, `other`
  в plural, метаданные), но настоящий `flutter gen-l10n` в CI всё равно нужен.
- Для языков без своего модуля работают только общие проверки.
